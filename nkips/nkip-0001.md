# NKIP-0001: Verifiable Deposit Receipts

Every swap order gets a receipt signed by the exchange before the deposit
address is shown, and an issuer-signed commitment to it is stored by
independent witnesses, so a dispute never depends on whether the user
remembered to download a letter of guarantee.

## Motivation

A letter of guarantee (LoG) protects a user only if they download it, and
most don't. Recent no-KYC swap disputes have come down to one side's word
against the other's because nobody kept a receipt.

Goals:

- **G1** Every order has a receipt the exchange signs and can't later deny.
- **G2** The receipt is saved by someone other than the user, without them doing anything.
- **G3** Anyone can check a disputed order without the exchange's cooperation.
- **G4** "No receipt" counts against the exchange, not the user.

Non-goals:

- Proving delivery on the user's behalf. Once a receipt and the deposit are proven, the issuer has to prove the payout (txid, or tx key for XMR payouts).
- KYC or identity of either party.
- A central registry of orders. Witnesses hold hashes, not plaintext addresses.

## Roles

| Role | Who | Job |
| --- | --- | --- |
| Issuer | The exchange | Signs a receipt for every order and publishes its signing key |
| User | The customer | Deposits only after the deposit address is shown; nothing to save |
| Witness | Nostr relays; aggregators routing the order | Store the attestation or receipt, independently of the issuer |
| Verifier | Any directory or tool implementing this NKIP | Pins issuer keys after domain-control verification, checks disputes |
| Log | Hourly Merkle roots of attestations (Nostr events, optional OpenTimestamps) | Proves an attestation existed at a given time |

## Specification

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

### Receipt

A JSON object signed by the issuer at order creation, before the deposit
address is shown. Schema: [`nkip-0001/receipt.schema.json`](nkip-0001/receipt.schema.json).

| Field | Meaning |
| --- | --- |
| `v` | Spec version, `nkip01/1` |
| `issuer` | Issuer domain, lowercase, e.g. `example.swap` |
| `order_id` | The issuer's order ID |
| `deposit_asset`, `deposit_address`, `deposit_amount` | What the user sends, and where |
| `payout_asset`, `payout_address`, `payout_amount` | What the issuer promises, and where; for `float` orders the amount is a quoted floor |
| `rate_type` | `fixed` or `float` |
| `created_at`, `expires_at` | Integer Unix seconds |
| `refund_address` | Optional |
| `policy_hash` | SHA-256 (hex) of the exact bytes of the refund/tolerance policy in force at order time |
| `salt` | v2 only: 32 bytes as 64 lowercase hex, see Commitment. `v` is then `nkip01/2` |
| `key_id` | First 8 bytes of SHA-256 of the signing public key, hex |
| `sig` | Ed25519 signature, base64url without padding |

Rules:

- Canonical form is RFC 8785 (JCS). Amounts are decimal strings in the asset's base unit (piconero, satoshi, ...). `sig` is computed over the JCS bytes of the receipt with the `sig` field removed.
- Ed25519 is the only v1 algorithm. A PGP-signed LoG MAY be offered as a human-readable copy, but it is not the receipt.
- `deposit_address` MUST be unique to the order. A reused address makes the order ambiguous, and a dispute on it counts against the issuer.
- Amount tolerance, partial or over-payment and late deposits follow the policy named by `policy_hash`.

### Issuer manifest (`nkip01.json`)

The issuer publishes `https://<issuer>/.well-known/nkip01.json`, served with
`Content-Type: application/json`. Schema: [`nkip-0001/manifest.schema.json`](nkip-0001/manifest.schema.json).

```json
{
  "v": "nkip01/1",
  "issuer": "example.swap",
  "adopted_at": 1793000000,
  "keys": [
    {
      "key_id": "3b1f0c9e5a7d2e41",
      "alg": "ed25519",
      "public_key": "<base64url, 32 bytes>",
      "not_before": 1793000000,
      "revoked_at": null,
      "rotated_from": null,
      "rotation_sig": null
    }
  ],
  "nostr_pubkey": "<hex, 32 bytes>",
  "relays": ["wss://relay.example.org", "wss://relay.example.net", "wss://relay.example.com"],
  "policies": [{"policy_hash": "<sha256 hex>", "url": "https://example.swap/policy/v1.txt"}],
  "disputes": {"email": "disputes@example.swap", "nostr": "<npub or hex>"}
}
```

- `keys[].rotation_sig` is the old key's signature (base64url) over the JCS of the new key entry without `rotation_sig`. A new key without it is valid only after the verifier re-checks domain control.
- `revoked_at` revokes a key. Receipts with `created_at >= revoked_at` are invalid. Earlier receipts stay valid only if their attestation is in a log root published before `revoked_at`.
- Every `policy_hash` used in a receipt MUST be listed with a URL serving those exact bytes. Policy URLs are never edited; a new policy gets a new URL. Verifiers SHOULD archive policy texts when they first see them.
- `adopted_at` starts the issuer's obligations. The "no receipt" rule (G4) applies to orders created 14 days or more after `adopted_at`.
- Verifiers MUST NOT pin a key on first sight. They pin only after a domain-control verification, and publish the pin in a signed feed.

### Commitment and attestation

- **Commitment (v2):** `SHA-256("nkip01/2" || 0x00 || issuer || 0x00 || deposit_address || 0x00 || payout_address || 0x00 || salt)`, lowercase hex, where `salt` is the receipt's 32 bytes. `order_id` is deliberately excluded; uniqueness of `deposit_address` links it to one order.
- **Why the salt.** An unsalted commitment can be recomputed by anyone who knows both addresses. When the deposit is on a transparent chain (BTC, LTC, EVM, ...) every deposit address is public, and the attestation's time narrows the candidates to a few minutes. An observer who knows a user's payout address (a published tip address, or a reused one) can then hash each candidate deposit with it and find the match, tying the user's deposit to that payout.
- **Choosing the salt.** When `deposit_asset` is on a transparent chain the issuer MUST use 32 random bytes. When `deposit_asset` is XMR the deposit address never appears on chain, so the issuer MAY use 32 zero bytes, and the user can then recompute the commitment from the two addresses alone.
- **Salt box (XMR payouts).** When the salt is random and `payout_asset` is XMR, the issuer MUST add a salt box to the attestation, so the user's wallet can recover the salt without anyone having saved it:
  - the payout address MUST be a standard address or subaddress; integrated addresses are refused at order creation;
  - pick a random non-zero scalar `r` (64 bytes from a CSPRNG, reduced mod ℓ); for a standard address publish `R = r·G`, for a subaddress `R = r·S` where `S` is the subaddress's public spend key;
  - compute the derivation `8·r·V`, where `V` is the address's public view key;
  - `salt_box = {"r": hex(R), "ct": hex(salt XOR SHA-256("nkip01/2 salt" || 0x00 || derivation))}`.

  The wallet computes the same derivation as `8·v·R` with its private view key and recovers the salt. The box's presence does reveal that the payout is XMR and the deposit is on a transparent chain; both are visible on chain anyway. Only the holder of that view key can do this; to everyone else `R` and `ct` look random. A verifier MAY offer a tool that does this on the user's device; the private view key MUST NOT leave that device.
- **Recovery key (other payouts).** When the salt is random and `payout_asset` is not XMR, there is no payout key to encrypt to. A client MAY send a `recovery_pubkey` (a 32-byte x-only secp256k1 public key, such as the user's Nostr key or one an extension generates) when creating the order; the issuer then MUST add `salt_nip44`, the salt as 64 lowercase hex characters encrypted to that key with NIP-44 v2 from the issuer's `nostr_pubkey`. Clients SHOULD send a recovery key by default. Like the salt box, its presence shows the payout isn't XMR and the deposit is transparent, which the chains show anyway. If the issuer later rotates its Nostr key, existing `salt_nip44` values still decrypt with the old public key, which stays listed in the manifest history. Without a recovery key the salt lives only in the receipt: the aggregator witness holds it for routed orders, and for other orders the user needs the receipt, which the issuer MUST offer for download. This is the one case where G2 holds only through a witness that keeps the full receipt.
- **Attestation:** the JCS object `{"v","issuer","commitment","created_at","key_id","salt_box"?,"salt_nip44"?,"sig"}`, where `sig` is the Ed25519 signature over the JCS of the other fields. `salt_box` and `salt_nip44` are signed, so they can't be swapped. The manifest's own `v` stays `nkip01/1` (it versions the manifest format); receipts and attestations carry their own `v`, and an issuer may publish both versions while it migrates.
- **v1** (`nkip01/1`, the unsalted form `SHA-256("nkip01/1" || 0x00 || issuer || 0x00 || deposit_address || 0x00 || payout_address)`) stays valid for attestations already published. Issuers SHOULD move to v2 for new orders at once and MUST use it for orders with a transparent-chain deposit created 14 days after this change. Unsalted v1 attestations already published stay linkable by the attack above; that residual risk can't be undone, so users of such orders SHOULD treat the payout address as linked to the deposit.

### Nostr event

The attestation is published as a Nostr event (NIP-01) signed by `nostr_pubkey`:

| Field | Value |
| --- | --- |
| `kind` | `3711` (provisional; to be registered upstream) |
| `content` | The attestation JSON |
| `tags` | `["c", <commitment>]`, `["i", <issuer>]`, `["v", "nkip01/2"]` (or `nkip01/1` for v1) |
| `created_at` | Equal to the attestation's `created_at` (±300 s) |

Anyone can find an attestation with the relay filter `{"kinds":[3711],"#c":[<commitment>]}`.

A verifier accepts the event only if the Nostr signature matches the manifest's `nostr_pubkey` and the Ed25519 signature matches a pinned key. Either key alone is not enough.

### Witnessing

Before showing the deposit address, the issuer MUST get an attestation into
at least one counted witness.

| Channel | Holds | Proves later | Counts |
| --- | --- | --- | --- |
| Nostr relays | The attestation event, on 3 or more relays the issuer doesn't control | The issuer committed to this deposit/payout pair at this time | Yes, with `OK true` from at least 2 relays |
| Aggregator | The full receipt, for orders it routes | The full terms of the order | Yes, with a signed acceptance |
| Browser extension | A local copy of the receipt | The full terms, if the user still has it | No |

- **Acceptance signal:** a NIP-01 `["OK", <event id>, true, ...]` from at least 2 relays not operated by the issuer, or an aggregator response that echoes the commitment. The order page SHOULD show the event id next to the deposit address.
- Nostr is the default path and needs no aggregator, so an aggregator outage never blocks a compliant issuer. Without an acceptance signal, the issuer MUST NOT show the address and retries.
- Aggregators SHOULD delete full receipts 180 days after `expires_at`.

### Releasing the deposit address (every channel)

R2 applies wherever the issuer hands out a deposit address: its web page, its
API, a CLI, a bot or a partner integration. Holding the address back only in
the web page does not satisfy it while an API response or the page's own data
already carries it.

Witnessing must not slow order creation down. The recommended pattern is to
create the order at once and release the address separately:

1. The create call returns immediately with the order and a `witness` object
   in state `pending`. `deposit_address` and `receipt` are `null`. (The issuer
   has already signed the receipt; it is just not handed out yet.)
2. The issuer publishes the attestation in the background and records each
   relay's `OK` with the order.
3. The order-status call (which clients poll anyway) returns the address and
   the full signed receipt once a counted witness has accepted, with the
   witness in state `accepted`.

```json
{
  "id": "EX-0001",
  "deposit_address": null,
  "receipt": null,
  "witness": {
    "state": "pending",
    "via": "nostr",
    "event_id": "<64 hex, kind 3711 event id>",
    "commitment": "<64 hex>",
    "relays_ok": 1,
    "required": 2
  }
}
```

Schema: [`nkip-0001/order-status.schema.json`](nkip-0001/order-status.schema.json).
The issuer's own order `status` field is unchanged; the `witness` object
carries the NKIP-0001 state:

| `witness.state` | Meaning | `deposit_address` and `receipt` |
| --- | --- | --- |
| `pending` | Published, not yet accepted by a counted witness | `null` |
| `accepted` | `via: "nostr"` with `relays_ok ≥ required ≥ 2`, or `via: "aggregator"` with the aggregator's signed acceptance in `acceptance` | Present |
| `failed` | Not accepted before the order would have to be re-issued (below); terminal | `null`; the order is cancelled |

- The issuer SHOULD mark the order witnessed as soon as the required number of
  relays has answered `OK true`, not after all of them, and SHOULD keep relay
  connections open between orders, so the address usually follows within about
  a second.
- An issuer MAY accept a `wait` parameter (at most 10 seconds) on create and
  return the address in the same response if the order is witnessed in time,
  for clients that want a single call.
- **Trust model.** At release time the client relies on the issuer's own
  record of relay `OK` responses; that is acceptable because the record is
  checkable later, and a missing attestation counts against the issuer ("No
  receipt" claims). Clients SHOULD NOT query relays for their own order's
  commitment right away, since a relay would then see the user's IP asking
  about it. A client that wants an independent check MAY do it later, over Tor
  and from a relay other than the one it uses for anything else.
- If no counted witness accepts within about 30 seconds, the issuer keeps
  retrying and tells the user it is still securing the record. It MUST NOT fall
  back to releasing the address.
- The deposit window is the receipt's signed `expires_at` and is never
  extended after signing. The issuer SHOULD set it to the usual window plus a
  witnessing allowance (60 seconds is plenty with the timings above). The
  usual window is the one the issuer's policy text (`policy_hash`) states. If
  the allowance is used up, so that less than that window would remain at
  release, the issuer marks the witness `failed`, cancels the order and the
  user creates a new one (a new deposit address and a new receipt). It never
  releases an address with a shortened window.
- The released `deposit_address` MUST equal the one in the released receipt.
- An issuer that keeps an older endpoint returning the address at once MUST
  document that endpoint as not conforming to R2 and SHOULD publish a sunset
  date for it. A claim of conformance (for example in an Implementations
  listing) covers only the conforming channels.

### Log

Batchers timestamp attestations. Anyone MAY run one, and a verifier MAY use several.

- Every hour, a batcher collects the kind 3711 events it saw in that hour and sorts their commitments. It builds a Merkle tree as in RFC 6962: leaf = `SHA-256(0x00 || commitment bytes)`, node = `SHA-256(0x01 || left || right)`.
- It publishes kind `3712` (provisional) with content `{"v":"nkip01/1","hour":<unix hour start>,"root":<hex>,"count":<n>,"leaves_url":<url>}`, and MAY anchor `root` with OpenTimestamps.
- The root's `v` versions the log format; its leaves may be v1 or v2 commitments, which look alike (32 bytes each).
- `leaves_url` serves the sorted commitment list. An inclusion proof is that list, or the audit path computed from it.
- Roots from different batchers need not agree, because each sees different relays. An attestation's existence time is the earliest root that includes it. A batcher that leaves out an event it demonstrably received is untrustworthy for that hour.

### Order and dispute flow

1. The user requests a quote and enters the payout address.
2. The issuer creates the order with a one-time deposit address and signs the receipt.
3. The issuer publishes the attestation event to its relays, and hands the receipt to the aggregator for routed orders.
4. Only after an acceptance signal does the page show the deposit address (and the event id).
5. The user deposits.
6. In a dispute, the user gives a verifier the deposit address, the payout address, the salt (from the receipt, from their wallet's salt-box recovery, or zero for an XMR deposit) and a deposit proof. For XMR that is the tx key (`check_tx_key`) or a `get_tx_proof` proof; for BTC, the txid.
7. The verifier recomputes the commitment, queries relays for the attestation (or checks a receipt), and checks the deposit on-chain.
8. The verifier notifies the issuer through `disputes` in the manifest. Within 7 days the issuer shows the payout (txid, or tx key for an XMR payout) to the committed payout address, or a refund under its policy.
9. No payout proof means a substantiated claim against the issuer. The verifier publishes the outcome either way.

v1 verifiers MUST support BTC and XMR deposits and payouts. Other chains MAY be supported where a deposit or payout can be proven from public data.

### "No receipt" claims

For orders created 14 days or more after `adopted_at`, a deposit to an address the issuer gave out with no attestation anywhere counts against the issuer. The claim needs an on-chain deposit plus at least one of these:

- a timestamped capture of the issuer's page showing the address (web archive, TLS notary or OpenTimestamps of the saved page);
- the same address in another attested order from that issuer;
- a message from the issuer's `disputes` contact, or its support, that names the address;
- the aggregator's routing record.

Without any of these, the claim is published as *unsubstantiated* and does not count.

## Security considerations

| Threat | Likelihood | Control |
| --- | --- | --- |
| Issuer skips the receipt for one order it plans to keep | High | Detect, don't prevent: an address shown without an attestation is unreceipted; extensions warn before deposit; the claim counts once the evidence standard is met |
| False "no receipt" claims | Medium | Evidence standard: an on-chain deposit plus proof the issuer gave out that address (timestamped page capture, the same address in another receipted order, or the issuer's admission); otherwise unsubstantiated |
| Issuer denies a receipt | Medium | Attestation signed with the pinned key, plus a timestamped root |
| User forges or edits a receipt | Medium | Signature fails; amounts must match the on-chain deposit |
| Replay | Low | One-time deposit address, `expires_at`, one deposit per receipt |
| Clipboard hijack of the payout address | Medium | Extension compares the on-page address with the receipt |
| Phishing clone | High | Key doesn't match the pin |
| Key substituted at first contact | Low | No first-sight pinning |
| Relays delete or censor events | Low | 3+ relays and independent hourly roots |
| Witness collusion | Low | Only issuer-signed attestations count: a witness can drop data but not forge it |
| Lapsed domain bought by someone else | Medium | Key pinned to the verifier's listing, not just the domain |
| The address leaks before witnessing through an API or the page's own data, while only the UI hides it | Medium | R15: every channel withholds it; status releases it after relay `OK`s |
| Witnessing makes ordering slow, so the issuer quietly drops R2 | Medium | Asynchronous release: create returns at once, the address follows on status (Releasing the deposit address) |
| Issuer key stolen | Low | Rotation signed by the old key; revocations published |
| Timing/amount correlation | Low | No amounts in the log; hourly batching |
| Linking a known payout address to a transparent-chain deposit by recomputing commitments | High for unsalted v1 when the payout address is known | v2 random salt (R16); salt box so XMR payouts still need nothing saved (R17); a fresh subaddress per swap payout (R18) |

## Test vectors

- `nkip-0001/vectors/v1.json` (v1): a signed receipt, its JCS bytes, a tampered receipt, an attestation and a Merkle root. Check with `python3 tools/nkip0001.py check nkips/nkip-0001/vectors/v1.json` (needs `pynacl`).
- `nkip-0001/vectors/v2.json` (v2): BTC→XMR receipts to a standard address and to a subaddress, each with its salted commitment and a signed attestation whose salt box opens with the test wallet's private view key (and not with another key), plus an XMR→BTC receipt with a zero salt. Check with `python3 tools/nkip0001.py check2 nkips/nkip-0001/vectors/v2.json` (needs `pynacl` and `pycryptodome`). The wallet is the throwaway NKIP-0003 test wallet; never send funds to it.
