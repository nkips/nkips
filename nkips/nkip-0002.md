# NKIP-0002: Verifiable Monero Tips on Nostr

A tipper publishes a receipt for a Monero tip. A payment proof goes only to
the recipient, encrypted, and the recipient publishes a confirmation, so
clients can show verified tip totals without any transaction id becoming
public.

## Motivation

Monero tips on Nostr are shown from receipts the tipper signs (kind 9042, as
shipped in RipleyOS). Any key can publish one for any amount, so totals built
from receipts alone can be inflated at no cost. A public transaction id would
make them checkable, but tying a tx hash to a Nostr identity links sender and
transaction, which is what Monero hides.

Only the recipient can check a payment without that link being public: their
wallet already sees the incoming transfer. This NKIP lets the recipient
confirm a tip, publicly and without the txid.

Goals:

- **G1** A client can tell a tip the recipient confirmed apart from one that is only claimed.
- **G2** No txid, tx key or payment proof is ever public.
- **G3** Clients that hold no wallet (browser extensions, web clients) can still tip, read totals and show which tips are verified.
- **G4** Receipts already published by RipleyOS stay valid; they count as claimed until confirmed.

Non-goals:

- Proving a tip to anyone other than the recipient.
- Lightning (NIP-57 zaps, kind 9735).
- Sending funds. Clients hand off to a wallet; nothing here moves money.

## Roles

| Role | Who | Job |
| --- | --- | --- |
| Tipper | The person tipping | Sends XMR from their wallet; signs the receipt |
| Recipient | The author being tipped | Publishes a NIP-A3 address; confirms tips that arrived |
| Wallet client | A Nostr client with a Monero wallet (e.g. RipleyOS) | Produces the payment proof and checks incoming proofs automatically |
| Viewer | Any client showing tips (e.g. a browser extension or web client) | Counts receipts and confirmations; needs no wallet |

## Specification

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.
Kinds 9042, 9043 and 9044 are provisional; 9042 is already in use by RipleyOS.
The authors will request these kinds upstream (nostr-protocol/nips). If different
kinds are assigned, a later version moves to them and readers accept both during
a transition of at least 12 months.

### Recipient address

The recipient's tip address is the first valid `["payto","monero"|"xmr",<address>]`
tag of their newest kind 10133 event (NIP-A3). `monero` is the canonical NIP-A3 type; `xmr` is accepted as an alias. A kind 0 `monero`, `xmr` or
`monero_address` field MAY be used when there is no kind 10133. Clients MUST
validate the address (mainnet, checksum) before showing it.

### Receipt (kind 9042)

Signed by the tipper after the send.

| Field | Value |
| --- | --- |
| `kind` | `9042` |
| `content` | `""` for new clients; legacy RipleyOS receipts carry `"xmr zap"`. Readers ignore it |
| `tags` | `["e", <note id>]` (omit for a profile tip), `["p", <recipient pubkey>]`, `["amount", <decimal XMR>]`, `["unit", "xmr"]`, `["address", <address paid>]`, `["client", <name>]`, optionally `["v", "nkip02/1"]` |

Rules:

- A receipt without a `v` tag is a legacy receipt and is read as `nkip02/1`. New clients SHOULD add the tag.
- A receipt has exactly one `p` tag and at most one `e` tag. Readers drop receipts with more.
- For a note tip, `p` MUST be the author of the note in `e`. Readers drop note receipts where it isn't.
- `address` MUST be a standard address or a subaddress (95 characters). Integrated addresses are not allowed.
- Readers MUST NOT render tags they don't know.
- `amount` is a decimal XMR string with at most 12 fractional digits (e.g. `"0.001"`), as RipleyOS publishes today. Readers convert to piconero with fixed-point arithmetic.
- A receipt MUST NOT carry a `txid`, `tx`, tx key or proof tag. Readers MUST ignore any such tag and SHOULD NOT display it.
- `address` MUST be the address the tipper actually paid. While a receipt is unconfirmed, it counts as claimed only if `address` is one of the recipient's current NIP-A3 or kind 0 addresses (see Counting for confirmed receipts).
- A tipping client SHOULD make the amount unique by adding 1–999,999 random piconero (at most 0.000001 XMR) to the amount the user chose (e.g. `0.001000437215`), and publish the exact amount sent. This keeps `wallet-match` from pairing a receipt with someone else's transfer.
- A wallet client SHOULD publish the receipt only after its wallet reports the send. A client without a wallet MUST ask the user to confirm the send before publishing, and MUST NOT publish without an amount.

### Payment proof (kind 9043, gift-wrapped)

The tipper's client sends the recipient a proof the recipient's wallet can check.

- The tipper's client MUST check that `address` in the proof equals the receipt's `address`.
- The proof is the Monero wallet's `get_tx_proof(txid, address, message)` output, with `message` set to the receipt's event id (lowercase hex). That ties the proof to one receipt, so it can't be reused for another.
- The client builds an unsigned rumor (NIP-59) of kind `9043` with tags `["p", <recipient>]`, `["e", <receipt id>]`, and content the JSON object below. It seals and gift-wraps it to the recipient per NIP-59 (NIP-44 encryption) and publishes the wrap to the recipient's NIP-65 read relays or kind 10050 DM relays.
- The proof MUST NOT be sent any other way, and MUST NOT be published unwrapped.

```json
{
  "v": "nkip02/1",
  "receipt": "<receipt event id, hex>",
  "txid": "<64 hex>",
  "address": "<address paid, same as the receipt>",
  "proof": "OutProofV2…"
}
```

Schema: [`nkip-0002/proof.schema.json`](nkip-0002/proof.schema.json).

`get_tx_proof` for an outgoing transfer needs the tx secret key, which the wallet stores when it sends. A wallet restored from seed has lost it for earlier sends and cannot make the proof; such tips can only be confirmed by `wallet-match`.

A wallet client SHOULD send the proof automatically. A client without a wallet MAY offer a field to paste the txid and proof from the user's wallet; it MUST NOT ask for the tx private key.

### Confirmation (kind 9044)

Signed by the recipient (the receipt's `p` key) once the tip has been checked.

| Field | Value |
| --- | --- |
| `kind` | `9044` |
| `content` | `""` |
| `tags` | `["e", <receipt id>]`, `["p", <tipper pubkey>]`, `["amount", <decimal XMR confirmed>]`, `["method", "tx-proof" \| "wallet-match"]`, `["t", <transfer tag>]`, `["v", "nkip02/1"]` |

The **transfer tag** lets viewers see that two confirmations point at the same
transfer without learning the txid:
`t = lowercase hex of HMAC-SHA256(k, txid)`, where `txid` is the 32 raw bytes and
`k = HKDF-SHA256(ikm = the wallet's private view key (32 raw bytes), salt = "nkip02", info = "transfer tag v1", L = 32)`. Salt and info are UTF-8 bytes with no terminator. `k` is derived inside the wallet and MUST NOT be exported. Wallet setups that never expose the view key to the confirming client cannot derive `k`, and therefore cannot confirm.

Confirming always needs the recipient's wallet (to check the proof or the
incoming transfer), so every confirming client can derive `k`, including clients
that sign Nostr events through NIP-07 or NIP-46. Every device with that wallet
derives the same `k`, so the same transfer always gets the same tag. Since txids
are public, a plain hash would reveal the txid to anyone who hashes the chain;
the key prevents that. HKDF is one-way, so a leaked `k` never reveals the view
key, but it does let the holder map this recipient's tags to txids.

Methods:

- **`tx-proof`**: the recipient's wallet ran `check_tx_proof(txid, address, receipt id, proof)`, got `good: true` and at least 10 confirmations, the proof's `address` equals the receipt's `address` and belongs to the recipient's wallet, and `amount` is the `received` value it returned (converted to decimal XMR).
- **`wallet-match`**: there was no proof. The recipient's wallet holds an incoming transfer to `address` (or one of its subaddresses) with exactly the receipt's amount, included in a block whose timestamp is between 2 hours before and 2 hours after the receipt's `created_at`, with at least 10 confirmations, and that transfer is not used for any other confirmation. This is weaker; clients MAY show it differently. A recipient's client MUST NOT confirm by `wallet-match` automatically: the recipient confirms each match by hand.

Rules:

- A confirmation MUST NOT contain the txid, tx key or proof.
- Per recipient, one transfer confirms at most one receipt. A transaction paying two recipients can be confirmed once by each. The recipient's client enforces this with the transfer tag, checking its own earlier confirmations on relays as well as local state, so a second device or lost state can't confirm the same transfer twice.
- If several receipts match one transfer, the one with the earliest `created_at` wins; ties go to the lowest event id (lexicographic hex). The others stay claimed.
- This rule binds honest clients. A dishonest recipient can still publish confirmations for tips that never happened; a confirmation is only ever the recipient's own word.
- While a transfer waits for its 10 confirmations (about 20 minutes), clients SHOULD show the tip as "verifying", not "unverified".
- If the recipient changes Nostr keys, receipts addressed to the old key can only be confirmed with the old key; otherwise they stay claimed.
- A recipient MAY withdraw a confirmation with a NIP-09 deletion (kind 5). Readers MUST then treat the receipt as claimed, and the transfer becomes free to confirm another receipt.
- A confirmation for an unknown receipt id is ignored until the receipt is seen.

### Counting

For a note (receipts with its `e` tag) or a profile (receipts with no `e` tag and its `p`):

1. Drop receipts that fail the receipt rules, receipts where the tipper is the recipient, and duplicate event ids. For note tips, drop receipts whose `p` isn't the note author.
2. A receipt is **verified** if a confirmation exists that references it, is signed by the receipt's `p` key (for note tips, the note author) and hasn't been deleted. Its verified amount is the lower of the receipt amount and the confirmed amount.
3. Viewers dedupe confirmations by (signer, transfer tag): when several share a tag, the one whose receipt has the earliest `created_at` (then lowest receipt id) counts, and the others' receipts stay claimed.
4. A verified receipt's address is vouched for by the recipient's confirmation, so it stays verified after the recipient changes its published address. The published-address check (R10) applies only to claimed receipts.
5. Every other remaining receipt is **claimed**. For claimed totals, count at most one receipt per tipper per note (the newest).
6. Clients SHOULD show the number of distinct tippers next to the verified total, and MAY weight or filter tippers by the viewer's web of trust (e.g. follows of follows).
7. Clients MUST label the two totals separately (for example `ɱ 0.004 ✓ +0.002 claimed`) and MUST NOT add them into a single number without saying so.

Clients SHOULD bound what they fetch, for example at most 500 receipts and 500 confirmations per note or profile, newest first, so a flood of fake events can't stall them. When a confirmation points at a receipt beyond the cap, clients fetch that receipt by id.

Relay filters:

- Receipts for notes: `{"kinds":[9042],"#e":[<note ids>]}`
- Confirmations: `{"kinds":[9044],"#e":[<receipt ids>],"authors":[<recipient>]}`, where the recipient for a note tip is the note author
- Tips to me: `{"kinds":[9042],"#p":[<my pubkey>]}`

### Flow

1. The viewer resolves the recipient address (NIP-A3) and shows a `monero:` URI or hands off to its wallet.
2. The tipper sends. A wallet client sees the send; a client without a wallet asks "Did you send it?".
3. The tipper's client publishes the receipt (kind 9042).
4. A wallet client creates the proof with `message` = receipt id and sends it gift-wrapped (kind 9043). A client without a wallet MAY forward a pasted proof the same way.
5. The recipient's wallet client unwraps it, runs `check_tx_proof`, and publishes a confirmation (kind 9044). With no proof, it MAY confirm by `wallet-match`.
6. Viewers show the verified and claimed totals.

## Security considerations

| Threat | Likelihood | Control |
| --- | --- | --- |
| Fake receipts inflating totals | High | Counted as claimed only, at most one per tipper per note; only confirmations make a tip verified |
| Proof reused for a second receipt | Medium | `get_tx_proof` message is the receipt id; one transfer confirms one receipt |
| Wash tipping: the recipient tips themselves from throwaway keys and confirms | High | Costs only network fees, since the funds come back. Viewers show distinct tippers and weight tippers by web of trust; a verified total means "the recipient says it received this", not popularity |
| Third party attaches self-confirmed tips to someone else's note | High | R12: a note receipt counts only when `p` is the note author, and only the author can confirm it |
| Recipient confirms one transfer for many receipts | Medium | Transfer tag plus viewer dedupe. A recipient who wants to lie can still confirm tips that never happened; a confirmation is only ever the recipient's own word |
| Recipient confirms tips that never arrived | Low | It's the recipient's own reputation; a confirmation only says "I got it". Viewers can weight by web of trust |
| Credit stealing: a receipt claims someone else's anonymous transfer | Medium | Random piconero in amounts; `wallet-match` is manual only; `tx-proof` binds the proof to the receipt id |
| Recipient refuses to confirm a real tip | Medium | The tip stays claimed; no funds are affected. The tipper still has the proof |
| txid leaked through the proof message | Low | Gift wrap hides sender, recipient and kind from relays; only the recipient decrypts |
| Recipient links the tipper's Nostr key to a transaction | Certain (by design) | The recipient learns which txid came from which key. Tippers who don't want that skip the proof; the tip then stays claimed or is matched by hand |
| Timing: receipt `created_at` close to the transaction on chain | Medium | Ring signatures hide the sender's input. Tippers who care MAY delay publishing the receipt |
| `wallet-match` confirms the wrong transfer | Medium | Exact amount and a 2-hour window; labelled as the weaker method |
| Receipt names an address the recipient doesn't control | Medium | R10: the address must be the recipient's published address |
| Confirmation from a different key | Low | R4: only the receipt's `p` key counts |

## Open questions

- [ ] Register kinds 9042, 9043 and 9044 upstream (nostr-protocol/nips), or pick replacements. 9042 is in use by RipleyOS.
- [ ] Amount unit: keep decimal XMR (compatible with existing receipts) or move to piconero like NKIP-0001 in a v2.
- [ ] Should viewers drop `wallet-match` confirmations by default?
- [ ] Test vectors need real `get_tx_proof` output from a stagenet wallet. **Test mode:** a reader in test mode accepts stagenet addresses instead of mainnet ones; nothing else changes. Production readers MUST NOT accept stagenet addresses.
