# SIP-0001: Verifiable Deposit Receipts

Every swap order gets a receipt signed by the exchange before the deposit
address is shown, and an issuer-signed commitment to it is stored by
independent witnesses, so a dispute never depends on whether the user
remembered to download a letter of guarantee.

## Motivation

A letter of guarantee (LoG) protects a user only if they download it, and
most don't. Recent no-KYC swap disputes have come down to one side's word
against the other's because nobody kept a receipt.

Goals:

- **G1** Every order has a receipt the exchange signs and can't later deny.
- **G2** The receipt is saved by someone other than the user, without them doing anything.
- **G3** Anyone can check a disputed order without the exchange's cooperation.
- **G4** "No receipt" counts against the exchange, not the user.

Non-goals:

- Proving delivery on the user's behalf. Once a receipt and the deposit are proven, the issuer has to prove the payout (txid, or tx key for XMR payouts).
- KYC or identity of either party.
- A central registry of orders. Witnesses hold hashes, not plaintext addresses.

## Roles

| Role | Who | Job |
| --- | --- | --- |
| Issuer | The exchange | Signs a receipt for every order and publishes its signing key |
| User | The customer | Deposits only after the deposit address is shown; nothing to save |
| Witness | Nostr relays; aggregators routing the order | Store the attestation or receipt, independently of the issuer |
| Verifier | Any directory or tool implementing this SIP | Pins issuer keys after domain-control verification, checks disputes |
| Log | Hourly Merkle roots of attestations (Nostr events, optional OpenTimestamps) | Proves an attestation existed at a given time |

## Specification

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

### Receipt

A JSON object signed by the issuer at order creation, before the deposit
address is shown. Schema: [`sip-0001/receipt.schema.json`](sip-0001/receipt.schema.json).

| Field | Meaning |
| --- | --- |
| `v` | Spec version, `sip01/1` |
| `issuer` | Issuer domain, lowercase, e.g. `example.swap` |
| `order_id` | The issuer's order ID |
| `deposit_asset`, `deposit_address`, `deposit_amount` | What the user sends, and where |
| `payout_asset`, `payout_address`, `payout_amount` | What the issuer promises, and where; for `float` orders the amount is a quoted floor |
| `rate_type` | `fixed` or `float` |
| `created_at`, `expires_at` | Integer Unix seconds |
| `refund_address` | Optional |
| `policy_hash` | SHA-256 (hex) of the exact bytes of the refund/tolerance policy in force at order time |
| `key_id` | First 8 bytes of SHA-256 of the signing public key, hex |
| `sig` | Ed25519 signature, base64url without padding |

Rules:

- Canonical form is RFC 8785 (JCS). Amounts are decimal strings in the asset's base unit (piconero, satoshi, ...). `sig` is computed over the JCS bytes of the receipt with the `sig` field removed.
- Ed25519 is the only v1 algorithm. A PGP-signed LoG MAY be offered as a human-readable copy, but it is not the receipt.
- `deposit_address` MUST be unique to the order. A reused address makes the order ambiguous, and a dispute on it counts against the issuer.
- Amount tolerance, partial or over-payment and late deposits follow the policy named by `policy_hash`.

### Issuer key

- The public key is published at `https://<issuer>/.well-known/sip01.json` (format TBD, see open questions).
- Verifiers MUST NOT pin a key on first sight. They pin only after a domain-control verification, and publish the pin in a signed feed.
- A key change is signed by the old key, or follows a fresh domain-control verification recorded in a public log. Revocations are listed in `sip01.json`.

### Commitment and attestation

- **Commitment:** `SHA-256("sip01/1" || 0x00 || issuer || 0x00 || deposit_address || 0x00 || payout_address)`, hex. The user can recompute it from their own wallet history without having saved anything. `order_id` is deliberately excluded; uniqueness of `deposit_address` links it to one order.
- **Attestation:** the commitment plus `created_at` and `key_id`, signed with the issuer key.

### Witnessing

Before showing the deposit address, the issuer MUST get an attestation into
at least one counted witness.

| Channel | Holds | Proves later | Counts |
| --- | --- | --- | --- |
| Nostr relays | The attestation as an issuer-signed event, on 3 or more relays the issuer doesn't control | The issuer committed to this deposit/payout pair at this time | Yes |
| Aggregator | The full receipt, for orders it routes | The full terms of the order | Yes |
| Browser extension | A local copy of the receipt | The full terms, if the user still has it | No |

- Nostr is the default path and needs no aggregator, so an aggregator outage never blocks a compliant issuer. If no relay accepts the event, the issuer MUST NOT show the address and retries.
- Anyone MAY run a batcher that publishes hourly Merkle roots of attestations. Two independent roots that agree settle the timestamp.
- The log holds hashes only. Aggregators SHOULD delete full receipts 180 days after `expires_at`.

### Order and dispute flow

1. The user requests a quote and enters the payout address.
2. The issuer creates the order with a one-time deposit address and signs the receipt.
3. The issuer publishes the attestation to Nostr, and hands the receipt to the aggregator for routed orders.
4. Only after a counted witness accepts does the page show the deposit address.
5. The user deposits.
6. In a dispute, the user gives a verifier the deposit address, the payout address and a deposit proof (tx key for XMR, txid for transparent chains).
7. The verifier recomputes the commitment, finds the issuer-signed attestation (or checks a receipt), and checks the deposit on-chain.
8. The burden of proof moves to the issuer: within 7 days it shows the payout (txid, or tx key for an XMR payout) to the committed payout address, or a refund under its policy.
9. No payout proof means a substantiated claim against the issuer.

## Requirements

| ID | Level | Goal | Requirement | Acceptance check |
| --- | --- | --- | --- | --- |
| R1 | MUST | G1 | Issuer signs a JCS/Ed25519 receipt with all required fields for every order | Test vectors pass; schema validates |
| R2 | MUST | G2 | Deposit address is not shown before an attestation is accepted by a counted witness | Order page exposes the event id |
| R3 | MUST | G1 | Key at `/.well-known/sip01.json`; rotations signed by the old key | Pin and rotation chain visible |
| R4 | MUST | G2 | Receipt is machine-readable on the order page (`<script type="application/sip01+json">`) and in the create-order API | Aggregator and extension parse it |
| R5 | MUST | G3 | Commitments and attestations carry no plaintext address or amount | Log sample check |
| R6 | MUST | G3 | Within 7 days of a valid claim, the issuer produces a payout or refund proof | Recorded either way |
| R7 | MUST | G2 | Attestations go to 3 or more relays the issuer doesn't control | Relay query finds the event |
| R8 | SHOULD | — | A human-readable LoG of the same receipt is offered for download | Manual |
| R9 | SHOULD | G3 | Order status opens with the order ID alone | Manual |
| R10 | MUST | G2 | Aggregators implementing this SIP reject quotes from SIP-0001 issuers that lack a valid receipt | Aggregator test |
| R11 | MUST | G3 | A public verify tool needs no account, keeps nothing after the check, and is rate-limited | Code review |
| R12 | SHOULD | G2 | Extensions save receipts locally only and warn before deposit when one is missing | Extension test |
| R13 | MUST | G3 | Verifier key/domain feeds are signed | Signature check |
| R14 | MUST | G1 | This SIP ships a JSON schema, test vectors and a version field; v1 receipts stay valid after later versions | CI on this repo |

## Security considerations

| Threat | Likelihood | Control |
| --- | --- | --- |
| Issuer skips the receipt for one order it plans to keep | High | Detect, don't prevent: an address shown without an attestation is unreceipted; extensions warn before deposit; the claim counts once the evidence standard is met |
| False "no receipt" claims | Medium | Evidence standard: an on-chain deposit plus proof the issuer gave out that address (timestamped page capture, the same address in another receipted order, or the issuer's admission); otherwise unsubstantiated |
| Issuer denies a receipt | Medium | Attestation signed with the pinned key, plus a timestamped root |
| User forges or edits a receipt | Medium | Signature fails; amounts must match the on-chain deposit |
| Replay | Low | One-time deposit address, `expires_at`, one deposit per receipt |
| Clipboard hijack of the payout address | Medium | Extension compares the on-page address with the receipt |
| Phishing clone | High | Key doesn't match the pin |
| Key substituted at first contact | Low | No first-sight pinning |
| Relays delete or censor events | Low | 3+ relays and independent hourly roots |
| Witness collusion | Low | Only issuer-signed attestations count: a witness can drop data but not forge it |
| Lapsed domain bought by someone else | Medium | Key pinned to the verifier's listing, not just the domain |
| Issuer key stolen | Low | Rotation signed by the old key; revocations published |
| Timing/amount correlation | Low | No amounts in the log; hourly batching |

## Open questions

- [ ] Floating-rate orders: sign a floor, or re-sign once the rate locks?
- [ ] Exact witness-acceptance signal (e.g. OK from 2 of 3 relays) and Nostr event kind
- [ ] Merkle inclusion-proof format and user log lookup
- [ ] Revocation: validity rule for receipts signed before a revocation
- [ ] `sip01.json` format; where the policy text behind `policy_hash` is hosted immutably
- [ ] v1 payout chains (BTC + XMR at minimum) and how payouts are checked
- [ ] Claim channel to the issuer and where dispute records live
- [ ] Fallback evidence types for "no receipt" claims
- [ ] Reference batcher; what happens when roots disagree
- [ ] Is OpenTimestamps worth the extra step?
- [ ] XMR deposits: tx key or outgoing proof?
- [ ] Grace period before "no receipt" counts against an issuer
